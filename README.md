# Critical Matters Response

A private pastoral-care application for church leaders to share sensitive life matters with their pastor. The React frontend and Node.js API deploy together as one application, with MongoDB as the database.

## What is included

- React + Vite frontend (not Next.js)
- Node.js + Express backend (not NestJS)
- MongoDB/Mongoose models using a connection string
- Secure HTTP-only cookie authentication
- Member registration and login with unique emails
- Password recovery without any email messages
- Separate church-leader and pastor dashboard experiences
- Confidential reports, editing, sensitivity and urgency labels
- Private report conversations between the author and pastor
- Pastor access to all reports, statuses, responses, and member accounts
- Responsive public website, authentication pages, dashboards, and profile management
- Production server that serves `frontend/dist`

## Local setup

Requirements: Node.js 20+ and a MongoDB connection string (MongoDB Atlas or a local MongoDB instance).

1. Install dependencies (the root post-install step also installs the frontend):

   ```bash
   npm install
   ```

2. Copy `.env.example` to `.env` and fill in the values:

   ```bash
   cp .env.example .env
   ```

   Generate a strong JWT secret, for example:

   ```bash
   openssl rand -base64 48
   ```

3. Start the development servers:

   ```bash
   npm run dev
   ```

   Open `http://localhost:5173`. Vite proxies `/api` requests to the Express server on port 5000.

## Pastor account

Set `ADMIN_EMAIL` and `ADMIN_PASSWORD` in `.env`. On startup, the application will:

- create that account with the `pastor` role if the email does not exist; or
- promote the matching existing account to pastor.

Public registration always creates a standard church-leader account, so a user cannot register themselves as pastor.

After the first production deployment, keep the environment variables in your platform's secure configuration. The bootstrap process does not overwrite an existing pastor's password.

## Password recovery without email

Registration displays a recovery key once. The user must save it. The forgot-password page asks for:

- the account email;
- the saved recovery key; and
- a new password.

The recovery key is stored as a bcrypt hash and cannot be read from the database. No confirmation or password-recovery email is sent.

## Production deployment (one application)

Use these commands on your hosting provider:

```bash
npm install
npm run build
npm start
```

Set `NODE_ENV=production` plus the required values from `.env.example`. Express serves the generated `frontend/dist` directory and handles the API under `/api`, so the frontend and backend use one domain and one deployment.

Typical platform settings:

- Build command: `npm install && npm run build`
- Start command: `npm start`
- Health check: `/api/health`

## Privacy and security behavior

- Every non-pastor report query is scoped by the authenticated user's database ID.
- Only the report owner and a pastor can view or reply to a report.
- Only a pastor can view all reports, change statuses, or manage member access.
- Passwords and recovery keys use bcrypt with a cost factor of 12.
- Sessions use signed JWTs in HTTP-only, same-site cookies.
- Authentication endpoints are rate-limited.
- Helmet supplies production security headers.
- Closed reports remain readable but cannot be edited or replied to.

For highly sensitive production use, also enable HTTPS at the host, restrict MongoDB network access, rotate secrets, maintain encrypted backups, and define a church data-retention policy.
